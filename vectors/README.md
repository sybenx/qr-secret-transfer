# Test vectors

Known answers for [QR_SECRET_TRANSFER.md](../QR_SECRET_TRANSFER.md) and the
profiles in [`profiles/`](../profiles/README.md). An implementation that
reproduces every value here has read the specification the way independent
readings of it did.

These are normative. Where a vector and an implementation disagree, and the
vector is confirmed to follow the specification text, the implementation is
wrong. Where a vector and the specification text disagree, the text wins and the
vector is a bug: [report it](https://github.com/sybenx/qr-secret-transfer/issues/new?template=spec-issue.yml).

Every key, nonce and identity in these files is a fixture chosen for the file.
None belongs to anybody, and none should ever be used for anything.

## Files

| File | Covers |
|---|---|
| `qrst-sas.json` | QRST §6: the commit, the transcript hash, and the five digits. Uses `nostr-nsec` as its profile identifier. |
| `frost-share-max.json` | The `frost-share` profile at its largest payload under the default maximum (a 32-member group, 2041 bytes), its P4 check, and the size of every layer of wrapping (QRST §4 P1, §11.6). |

The test suite (`npm test`) checks `qrst-sas.json`.

## Provenance

`qrst-sas.json` was generated by an implementation written separately from the
one it tests, so a misreading of §6 has to be made twice to pass, and was then
reproduced a third time directly from the specification prose. The commit for
both flows, the code, the digits, and the roles-transposed negative case all
agree.

`frost-share-max.json` was built from a real secp256k1 keyset with a seeded
dealer. Its generator is not published, so it is a fixture to check against, not
one to regenerate; a real dealer MUST NOT use a seeded generator. Its P4 check and
its sizes were re-derived independently on 2026-10-17. Its encodings are bifrost's own `bfshare` and `bfgroup` formats. Its
`chain` sizes come from [`tools/payload_ceiling.py`](../tools/payload_ceiling.py)
for the 1.6 message shape (PAYLOAD rumor kind 24405 without tags, seal, ephemeral
gift wrap kind 21059). Both moved here from
[sybenx/nostr-key-management](https://github.com/sybenx/nostr-key-management) on
2026-10-17; the `frost-share` vector had been written for that repository's
unpublished 10.0 draft and was updated for 1.6, which made the wrap one byte
longer.

## What is still missing

- **A vector at exactly 2048 bytes.** P1 requires a conformance vector at exactly
  the declared maximum. `frost-share-max.json` comes within 7 bytes of it, but no
  vector sits on it. This is the case where NIP-44's power-of-two padding makes an
  off-by-one-chunk error invisible everywhere else, which is precisely why P1 asks
  for it.
- **A §11.4 gift-wrap vector.** One was drafted but never published. Its fixture
  predates 1.5, which made every timestamp true time, and 1.6, which moved the wrap
  to kind 21059, so it has to be regenerated before it can be normative.

## Checking an implementation

For §6, with the profile identifier `p` as ASCII:

```
commit = SHA-256("qrst-commit" || v || C.pub || nonce_C)
code   = SHA-256("qrst-sas" || v || len(p) || p
                 || SND.pub || RCV.pub || nonce_S || nonce_R)
digits = (code[0..5] as u40 BE) mod 100000, zero-padded to 5
```

`v` is the protocol version as a single byte (`0x01` for `v=1`).

`SND.pub` and `RCV.pub` are in role order regardless of which party made
contact. `code_with_roles_transposed` exists to catch the implementation that
gets that backwards, since it will otherwise agree with itself and fail only
against a real peer.
